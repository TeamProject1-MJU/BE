# 지하철 그래프·혼잡도 스키마 (#48)

기준은 ERD v1.13(`docs/erd_v1.13_20261029.dbml.txt`)과 API 명세 v1.12 부록 A다. `V10__create_subway_graph_and_congestion.sql` 하나로 추가하며 V1~V9와 V4의 stations는 변경하지 않는다.

## 테이블

| 테이블 | 역할 | 키·인덱스 |
| --- | --- | --- |
| subway_lines | 노선(코드, 이름, `#RRGGBB` 색, 정렬 순서) | `uq_lines_code (line_code)` |
| station_lines | 그래프 노드 = (역, 노선). 노선 안 순서 seq, 분기 branch_code(기본 `MAIN`) | `uq_sl_station_line (station_id, line_id)`, `uq_sl_line_code (line_id, station_code)`, `uq_sl_line_branch_seq (line_id, branch_code, seq)` |
| station_connections | 방향 있는 간선. RIDE(같은 노선 이동)·TRANSFER(환승) | `uq_conn_from_to (from_station_line_id, to_station_line_id)`, `idx_conn_to (to_station_line_id)` |
| congestion_stats | 노드·방향·요일 유형·30분 슬롯별 혼잡도 | `uq_cong_slot_source (station_line_id, direction, day_type, slot_start, source)` |

PK는 stations와 같은 `bigint generated by default as identity`다. enum 컬럼은 PostgreSQL enum 타입 없이 varchar + CHECK이며, 길이는 허용값 최대 길이(connection_type 8, direction 5, day_type 8, source 9)를 쓴다.

FK는 `fk_sl_station`, `fk_sl_line`, `fk_conn_from`, `fk_conn_to`, `fk_cong_station_line`이다. ERD Ref에 삭제 동작이 없으므로 PostgreSQL 기본값(NO ACTION)을 쓴다. 참조 중인 역·노선·노드는 삭제할 수 없다. 데이터 교체 방식은 아래 "적재 정책"을 따른다.

엔티티를 붙일 때: `subway_lines.color`는 ERD대로 `char(7)`(PostgreSQL `bpchar`)이다. Hibernate는 String을 varchar로 기대하므로, `ddl-auto=validate`를 통과하려면 필드에 `@JdbcTypeCode(SqlTypes.CHAR)`가 필요하다(`refresh_tokens.token_hash`와 같은 방식).

## CHECK 제약 (부록 A 이름 그대로)

| 이름 | 조건 |
| --- | --- |
| ck_lines_color | `color ~ '^#[0-9A-Fa-f]{6}$'` |
| ck_sl_seq | `seq >= 1` |
| ck_conn_not_self | from ≠ to |
| ck_conn_dir | RIDE면 direction 필수, TRANSFER면 direction null |
| ck_conn_nonneg | `travel_seconds > 0 and distance_m >= 0` |
| ck_conn_type | RIDE, TRANSFER |
| ck_conn_direction_val | null 또는 UP, DOWN, INNER, OUTER, LOOP |
| ck_cong_pct | `congestion_pct >= 0` |
| ck_cong_slot | 분이 0 또는 30이고 06:00~23:00 (35개 슬롯) |
| ck_cong_model | PREDICTED일 때만 model_version 있음 |
| ck_cong_level | 단계와 pct 구간 일치: COMFORTABLE [0,35), RELAXED [35,50), NORMAL [50,100), CROWDED [100,150), VERY_CROWDED [150,∞) |
| ck_cong_direction | UP, DOWN, INNER, OUTER, LOOP |
| ck_cong_day | WEEKDAY, SATURDAY, SUNDAY |
| ck_cong_source | PREDICTED, MOCK (ACTUAL 없음) |

congestion_level_label에는 CHECK를 두지 않는다. ERD는 단계에만 "pct와 일치 CHECK"를 적었고, 라벨은 "AI 파일 값 그대로" 저장한다고 적었다. 부록 A에도 라벨 제약은 없다. 라벨과 단계의 대응은 적재 스크립트에서 검증한다.

## 적재 순서

1. subway_lines
2. station_lines (stations는 V4에 이미 있고 먼저 적재되어 있어야 한다)
3. station_connections (RIDE, TRANSFER)
4. congestion_stats

FK 때문에 이 순서를 지켜야 한다.

## 적재 정책

ID가 바뀌면 안 된다. stations는 사용자 데이터(meeting_rooms.selected_station_id, meeting_members.departure_station_id, station_proposals, recommendation_results)가 NO ACTION으로 참조하므로, 방이 하나라도 생기면 지울 수 없다. 그래프 테이블은 사용자 데이터가 참조하지 않지만, 지우고 다시 넣으면 identity ID가 바뀌어 recommendation_results.trips(jsonb)나 서버 캐시에 남은 station_line_id가 어긋난다.

- stations는 삭제하지 않는다. 더 이상 지원하지 않는 역은 `is_supported = false`로 바꾼다. stations에는 ERD상 자연키 유니크가 없으므로, 적재 스크립트가 기존 행을 찾는 기준(예: station_lines의 `(line_id, station_code)`를 거쳐 역 찾기)을 정해 기존 ID를 재사용한다.
- 그래프 테이블은 자연키 기준 upsert(`insert ... on conflict (...) do update`)로 ID를 유지한다.
  - subway_lines: `line_code`
  - station_lines: `(line_id, station_code)`
  - station_connections: `(from_station_line_id, to_station_line_id)`
  - congestion_stats: `(station_line_id, direction, day_type, slot_start, source)`
- 새 데이터에 없는 간선·혼잡도 행은 삭제할 수 있다(다른 테이블이 참조하지 않는다). 노드(station_lines)는 그 노드를 참조하는 간선·혼잡도를 먼저 지운 뒤에만 삭제된다.
- 적재 스크립트가 id를 직접 지정해 넣으면 `generated by default` 시퀀스가 따라오지 않는다. 적재 후 테이블마다 `select setval(pg_get_serial_sequence('<table>', 'id'), (select max(id) from <table>))`를 실행한다.

## 적재 스크립트 검증 항목

DB CHECK는 값의 형식만 본다. 아래 의미 규칙은 DB가 보장하지 않으므로 적재 전에 스크립트가 검증하고 위반 행은 거부한다. 틀린 간선은 오류 없이 경로 탐색 결과만 틀어지게 만든다.

- RIDE: from과 to가 같은 노선(`line_id`)의 노드다.
- TRANSFER: from과 to가 같은 역(`station_id`)이고 노선이 다르다.
- direction:
  - INNER·OUTER는 2호선 본선 순환 RIDE에만 쓴다.
  - LOOP는 6호선 응암순환 구간 RIDE에만 쓴다. 응암순환은 한 방향 간선만 있고 상행·하행 구분이 없다(명세 6.1·13장).
  - 그 밖의 RIDE와 지선은 UP·DOWN을 쓴다. 지선은 분기점에서 멀어지면 DOWN, 분기점 쪽이면 UP이다.
  - congestion_stats.direction도 같은 기준으로 그 노드의 노선에 맞는 값만 쓴다.
- congestion_level_label과 congestion_level의 대응: 쾌적·COMFORTABLE, 여유·RELAXED, 보통·NORMAL, 혼잡·CROWDED, 매우 혼잡·VERY_CROWDED.
- color는 대문자 `#RRGGBB`로 통일한다. DB CHECK는 소문자도 허용한다.
- slot_start는 `HH:MM`(초 0)만 넣는다. 아래 "명세 부록 A와 ERD의 차이"를 참고한다.

DB로 강제하려면 station_lines에 `(id, line_id)`·`(id, station_id)` 유니크를 두고 간선에 복합 FK를 거는 방법이 있다. ERD 변경이 필요하므로 이번 범위에는 넣지 않았다.

## 조회 우선순위

uq_cong_slot_source에 source가 포함되므로 같은 슬롯에 PREDICTED와 MOCK이 함께 있을 수 있다. 조회 API는 PREDICTED가 있으면 PREDICTED, 없으면 MOCK 하나만 내려준다(명세 6.2, ERD congestion_stats.source 주석).

데이터 형태 메모:
- 2호선 순환 닫힘은 seq가 거꾸로 가도 간선의 direction으로 표현한다(충정로(43) → 시청(1) = INNER, 시청 → 충정로 = OUTER).
- 지선(성수지선, 신정지선, 마천지선)은 같은 line_id 안에서 branch_code를 달리하고 seq를 1부터 다시 센다. 분기점 역은 본선 노드 하나만 가진다.
- TRANSFER는 방향별 행이고 A→B와 B→A 값이 다를 수 있다.
- `(line_id, branch_code, seq)` 유니크가 실제 데이터에서 성립하는지는 적재 때 확인한다(명세 15장 확인 항목).

## 명세 부록 A와 ERD의 차이

- **ACTUAL**: ERD v1.13 `congestion_source`와 부록 A `ck_cong_source`는 모두 PREDICTED·MOCK만 허용하므로, 현재 제약 정의 자체는 서로 일치한다. 다만 명세 v1.9 변경 이력에 "ACTUAL·MOCK은 적재 시 같은 기준으로 단계·라벨을 채우고"라는 문구가 남아 있다. v1.12에서 ACTUAL을 사용하지 않기로 했으므로 이 문구는 과거 기준이며, 이번 스키마는 v1.12와 ERD v1.13에 따라 ACTUAL을 거부한다. MOCK은 적재 시 단계·라벨을 채운다.
- ck_cong_slot은 부록 A의 식을 그대로 쓴다. 초 단위는 검사하지 않으므로 `06:00:15`처럼 초가 있는 값은 통과하고, `06:00`과 다른 값으로 취급돼 같은 슬롯이 유니크 제약을 우회해 두 번 들어갈 수 있다. 적재 스크립트는 `HH:MM`만 넣는다. `extract(second from slot_start) = 0` 추가는 부록 A 수정과 함께 명세 담당자와 논의한 뒤 후속 마이그레이션으로 다룬다.

## 테스트

`SubwaySchemaMigrationPostgresTest`는 Testcontainers의 PostgreSQL 16에서 다음을 확인한다.
- 빈 DB에서 V1~V10 적용, V9 DB에서 V10 적용, validate와 재실행
- 컬럼 타입·NOT NULL·기본값과 enum 타입 미사용
- 제약 이름 14개, 유니크 6개, `idx_conn_to`, FK 삭제 동작
- 각 CHECK·유니크·FK 위반 거부
- 2호선 순환·분기·환승·혼잡도 정상 행과 단계 경계값

마이그레이션 테스트는 전체 마이그레이션 개수나 전체 테이블 목록을 고정하지 않는다. 적용 후 남은(pending) 마이그레이션이 0개인지와 자기 도메인 테이블만 확인하므로, V11 이후가 추가돼도 관계없는 테스트가 깨지지 않는다.
